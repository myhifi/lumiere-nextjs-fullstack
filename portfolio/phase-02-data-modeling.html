2 Architectural Decision — Single Source of Truth

Why one declarative schema.prisma instead of separate SQL, ORM models, and migrations?

ConcernAlternativeChosen (single schema.prisma)
Data definitionSQL DDL + ORM + migrations separatelyOne file generates all three
Type generationManual TypeScript interfacesAuto-generated PrismaClient types
MigrationsHand-written SQLprisma migrate dev diffs + writes SQL
IDE supportManual type annotationsFull autocomplete on every query
Engineering rationale One declarative file eliminates drift between database, application types, and documentation. Any change begins in schema.prisma and cascades down automatically.

7 Step 1 — Category & MenuItem Models

model Category {
  id           String     @id @default(cuid())
  name         String     @unique
  slug         String     @unique
  description  String?
  displayOrder Int        @default(0)
  createdAt    DateTime   @default(now())
  updatedAt    DateTime   @updatedAt
  items        MenuItem[]

  @@map("categories")
}

model MenuItem {
  id          String   @id @default(cuid())
  name        String
  slug        String   @unique
  description String?
  price       Float
  imageUrl    String?
  isAvailable Boolean  @default(true)
  isFeatured  Boolean  @default(false)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  categoryId  String
  category    Category @relation(fields: [categoryId], references: [id], onDelete: Cascade)

  @@map("menu_items")
}

HOW: Declares two related tables. Category owns MenuItem via a foreign key.

WHY: Separating categories from items allows filterable menus (/menu?category=desserts) without duplicating category names in every row.

@updatedAtAuto-updates on writeZero-maintenance last-modified tracking

@default(0)Numeric defaultSafe sort key for display order
@@map("...")Physical table nameKeeps DB names snake_case

9 Relation Semantics — @relation Explained

categoryId  String
category    Category @relation(fields: [categoryId], references: [id], onDelete: Cascade)
  • categoryId String — the foreign key column stored in menu_items.
  • category Category — the TypeScript accessor for the related row (item.category.name).
  • fields: [categoryId] — which local column holds the FK value.
  • references: [id] — which column in the parent table it points to.
  • onDelete: Cascade — deleting a category deletes all its items.
Why Cascade here Orphaned menu items (pointing to a deleted category) break queries and confuse admins. Cascade enforces referential integrity without manual cleanup.

12 Step 2 — Table & Reservation Models

model Table {
  id           String   @id @default(cuid())
  number       Int      @unique
  capacity     Int
  location     String?
  isActive     Boolean  @default(true)
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt
  reservations Reservation[]

  @@map("tables")
}

model Reservation {
  id              String   @id @default(cuid())
  guestName       String
  guestEmail      String
  guestPhone      String
  guestsCount     Int
  reservationDate DateTime
  durationMinutes Int      @default(90)
  status          String   @default("PENDING")
  notes           String?
  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt

  tableId String
  table   Table  @relation(fields: [tableId], references: [id])

  @@map("reservations")
}

HOW: Reservation links to Table via tableId. No onDelete: Cascade.

WHY No Cascade: Deleting a table must not destroy historical reservation records — those are financial/legal artifacts.

13 Design Decision — Status Field & SQLite Enum Limitation

Approach: Use String with @default("PENDING") rather than a native enum.

Valid statuses (application convention)

  • PENDING — created, awaiting staff confirmation
  • CONFIRMED — staff-approved
  • CANCELLED — cancelled by guest or staff
  • COMPLETED — guest dined, record closed

HOW: Prisma supports enums natively except on SQLite, which lacks the ENUM type.

WHY String for now: Keeping String allows the same schema to run on SQLite (dev) and PostgreSQL (prod, Phase 9) without edits. At migration time to Postgres, this field converts to a native enum in one line.

15 Step 3 — Seed Data Strategy

Why seed data matters

  • Empty DB → empty UI → nothing to test.
  • Realistic data (Arabic names, realistic prices) validates Arabic rendering and RTL flow.
  • Repeatable: npm run db:seed wipes and re-populates deterministically.

Modular structure chosen

prisma/
├── data/
│   ├── categories.ts    ← static arrays
│   ├── menu-items.ts
│   └── tables.ts
└── seed.ts              ← orchestrator (imports data, writes to DB)

Engineering rationale: Separating data (data/) from logic (seed.ts) means non-developers can adjust menus without touching orchestration code.

17 prisma/seed.ts — Orchestrator

import 'dotenv/config'
import { PrismaClient } from '../src/generated/prisma/client'
import { categories } from './data/categories'
import { menuItems } from './data/menu-items'
import { tables } from './data/tables'

const prisma = new PrismaClient()

async function main() {
  console.log('🌱 بدء زرع البيانات...')

  await prisma.reservation.deleteMany()
  await prisma.menuItem.deleteMany()
  await prisma.category.deleteMany()
  await prisma.table.deleteMany()
  console.log('🧹 تم تنظيف الجداول')

  for (const category of categories) {
    await prisma.category.create({ data: category })
  }
  console.log(`📂 تم إنشاء ${categories.length} تصنيفات`)

  for (const item of menuItems) {
    const { categorySlug, ...itemData } = item
    const category = await prisma.category.findUnique({
      where: { slug: categorySlug },
    })
    if (!category) throw new Error(`❌ التصنيف "${categorySlug}" غير موجود`)
    await prisma.menuItem.create({
      data: { ...itemData, categoryId: category.id },
    })
  }
  console.log(`🍽️  تم إنشاء ${menuItems.length} أطباق`)

  for (const table of tables) {
    await prisma.table.create({ data: table })
  }
  console.log(`🪑 تم إنشاء ${tables.length} طاولات`)

  console.log('✨ اكتمل زرع البيانات بنجاح!')
}

main()
  .catch((error) => { console.error('❌ خطأ أثناء الزرع:', error); process.exit(1) })
  .finally(async () => { await prisma.$disconnect() })

Line-by-line rationale

  • import 'dotenv/config' — loads .env BEFORE Prisma Client initializes (critical — see Slide 20).
  • deleteMany() order — child tables first to avoid FK violations.
  • const { categorySlug, ...itemData } — destructures out the helper field, keeping the DB payload clean.
  • findUnique({ where: { slug } }) — resolves category FK by slug, avoiding hardcoded CUIDs.
  • main().catch(...).finally(...) — guarantees connection cleanup and non-zero exit on failure.

18 Why tsx? — The TypeScript Executor

npm install tsx --save-dev

What tsx does: Accepts .ts file → transpiles on the fly → runs on Node.js. Uses esbuild (Go-based) for transpilation. Handles both CommonJS and ESM seamlessly.

WHY needed here:

  • Node.js cannot run .ts natively (as of Node 24 without experimental flags).
  • seed.ts imports from src/generated/prisma/client — a TypeScript module.
  • No compile step, no output directory, no tsconfig target confusion.

Alternatives rejected

  • ts-node — slower, ESM friction.
  • esbuild-register — less maintained.
  • Compile to .js first — extra step, stale files.

19 The dotenv Loading Failure & Fix

Symptom PrismaClientInitializationError: error: Environment variable not found: DATABASE_URL.

Root cause: tsx does NOT auto-load .env. Running tsx prisma/seed.ts starts Node.js, which reads process.env — but .env was never parsed.

Tool-by-tool .env behavior

ToolAuto-loads .env?
next devYes (Next.js handles it)
prisma migrateYes (via prisma.config.ts)
tsx prisma/seed.tsNo ← here's the problem

Fix (one line at top of seed.ts):

import 'dotenv/config'

HOW: dotenv/config reads .env and merges into process.env at import time — before new PrismaClient() executes.

WHY the top of the file: ES module imports execute in declaration order. Placing the dotenv import first guarantees .env is populated before Prisma's engine initialization.

23 Data Flow (Phase 2 Scope)

Phase 2 introduces no HTTP endpoints, but establishes the write path used by every subsequent phase:

Developer terminal ↓ npm run db:seed → tsx loads .env → Prisma Client ↓ Prisma Client → SQLite engine (query_engine-windows.dll.node) ↓ dev.db (single file on disk) ↓ prisma/migrations/ records the schema diff ↓ src/generated/prisma/ exposes typed API for future use

Boundary rationale: Data flows one direction only during seeding — developer intent → disk. No browser involvement, no HTTP layer, no serialization cost.
