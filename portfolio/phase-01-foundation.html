Phase 01 · Foundation

Project Foundation & Environment Setup

Establish a production-grade foundation for a single-codebase full-stack restaurant application. This phase configures Next.js 16, TypeScript, Tailwind CSS, Prisma 6, and a local SQLite database — all without a single paid service or credit card.

Next.js 16TypeScript 5Prisma 6 SQLiteTailwind CSS 4Node.js 24

1 Overview

Goal: Move from an empty directory to a working Next.js application with a validated Prisma schema pointing at a local database — the foundation every subsequent phase builds on.

Deliverables

  1. A working Next.js 16 application served on http://localhost:3000.
  2. A stable, pinned Prisma 6 installation — not the RC branch.
  3. A committed, validated schema.prisma with SQLite datasource.
  4. A clean package.json free of experimental postinstall hooks.
  5. npx prisma validate returns success.

2 Architectural Decision

Why a single Next.js codebase instead of keeping Django as a separate backend?

ConcernTwo-Server (Django + Next.js)Single-Codebase (Next.js)
LanguagesPython + TypeScriptTypeScript only
Deployments2 servers, 2 CI pipelines1 Vercel project
API boundaryHTTP round-trip between serversDirect function call in same process
Database clientsDjango ORM + PrismaPrisma only
Type safetyNot end-to-endEnd-to-end (Zod + TS + Prisma)
Engineering rationale Eliminating the network boundary between frontend and backend removes serialization cost, CORS configuration, and duplicated authentication logic. Server Components query Prisma in the same Node process.

10 Step 5 — Prisma Setup (with RC Downgrade)

Critical Fix npx prisma init initially installed prisma@8.0.0-rc.15, which created unexpected folders (.claude/, .cursor/, .agents/, .devin/) and failed to generate schema.prisma. This is an unstable pre-release.

Downgrade & Reinitialize

npm uninstall prisma @prisma/client
Remove-Item -Recurse -Force .claude, .cursor, .agents, .devin
del prisma.config.ts
npm install prisma@6 --save-dev
npm install @prisma/client@6
npx prisma init --datasource-provider sqlite
npm install dotenv --save-dev
npx prisma validate

HOW: Removes experimental dependencies and their side-effect artifacts, then reinstalls the current stable major (6.x).

WHY: RC = Release Candidate = feature-frozen but not production-hardened. RC APIs change without notice; stable versions have documented behavior and community support.

The schema at prisma\schema.prisma is valid 🚀

11 Configuration Files

prisma/schema.prisma

generator client {
  provider = "prisma-client"
  output   = "../src/generated/prisma"
}

datasource db {
  provider = "sqlite"
  url      = env("DATABASE_URL")
}
  • output places the generated client inside src/, not node_modules — makes it visible in the repo tree, allows IDE navigation.
  • provider = "sqlite" — file-based, zero-install, perfect for development.
  • url = env(...) — injects the connection string from .env, keeping secrets out of source.

.env

DATABASE_URL="file:./dev.db"

HOW: Prisma CLI resolves ./dev.db relative to prisma/ directory → creates prisma/dev.db.

WHY: The prisma/ folder is the natural home for local database files. One line replaces this with a hosted PostgreSQL URL at deploy time.

Runtime caveat Next.js resolves ./ relative to the project root, not prisma/. This mismatch is fixed in Phase 2 inside src/lib/prisma.ts using an absolute path.

prisma.config.ts

import "dotenv/config";
import { defineConfig, env } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",
  migrations: { path: "prisma/migrations" },
  engine: "classic",
  datasource: { url: env("DATABASE_URL") },
});
  • import "dotenv/config" — loads .env before Prisma reads it. Mandatory in Prisma 6.
  • defineConfig — typed configuration helper; enables IDE autocomplete.
  • engine: "classic" — uses the Node-API query engine for max performance on Windows.

12 Request Data Flow (Phase 1 Scope)

Phase 1 introduces no HTTP endpoints, but establishes the runtime dependency chain:

Browser → Next.js Dev Server (port 3000)
             ↓
             Reads .env → DATABASE_URL
             ↓
             Instantiates Prisma Client (generated in src/generated/prisma)
             ↓
             Connects to prisma/dev.db (SQLite)

Boundary rationale: Secrets flow one direction only — from .env into server processes. Nothing reaches the browser.
