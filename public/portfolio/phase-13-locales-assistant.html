Seven Locales, Zero-Download Chatbot

Extend the platform from 5 to 7 locales by adding Italian and Mandarin Chinese, then introduce the Smart FAQ Assistant — a floating chat panel that answers common restaurant questions in every language with zero external API, zero download, and sub-50ms responses. Pure TypeScript intent matching, no LLM.

next-intl 7 localesItalian 🇮🇹 Chinese 🇨🇳Self-contained assistant Intent MatcherPriority Tie-Break

1 Overview

Goal: Extend the reach of the existing 5-locale infrastructure to 7, and add a genuinely useful interactive feature that demonstrates a different class of engineering — algorithmic matching under tight cost and latency constraints.

Deliverables

  1. Italian locale — messages/it.json (~400 keys) + routing + switcher + email date locale.
  2. Chinese locale — messages/zh.json with ICU plural rules adapted for Chinese (single-form other).
  3. Smart FAQ Assistant — a floating chat panel with 10 intents supported in 7 languages.
  4. Serverless — pure TypeScript keyword matcher, no LLM, no external API, no data download.
  5. Priority tie-break — explicit policy for when two intents match a single query.
  6. Duplicate-keyword dedupe — defensive fix for cross-language keyword collisions.
  7. Responsive UI — bottom-left trigger above WhatsApp, panel that works on phones and desktops.
  8. Full test matrix — verification across all 7 locales for all 10 intents.

2 Two Features, One Phase

Both features share the same release cycle, and their paths converge on the same underlying principle: Direct server-side data access.

The shared principle
  • Locales — never call a translation API at runtime; every string lives in a JSON file.
  • Assistant — never call an LLM at runtime; every answer lives in a translation file too, chosen by a pure matcher.

9 Part 1 · The .next Cache Issue

Symptom After adding it.json and zh.json, navigating to /it and /zh throws: 
Cannot find module './it.json'

Root cause: Next.js/webpack caches the module context for dynamic import() calls. When request.ts contains:

messages: (await import(`../../messages/${locale}.json`)).default,

Webpack builds a static list of files matching ../../messages/*.json at build time. Adding a new file to that directory does not invalidate the cached context.

Fix — always after adding a new locale file:

Ctrl+C
Remove-Item -Recurse -Force .next
npm run dev
Rule to remember Any time you add a file that's imported via a template-literal dynamic import, clear .next and restart. This is a Next.js quirk, not a bug in the project.

10 Part 2 · Why Not an LLM

The instinctive design for a "Smart Assistant" is to plug in an LLM (ChatGPT, Claude, Gemini) via an API. Every option was evaluated and rejected:

OptionWhy it doesn't fit
WebLLM (Llama/Phi)1-2 GB download on first visit. Kills mobile users immediately.
Transformers.js30-150 MB download, unreliable on mobile Safari (WebGL throttling).
The actual winner A pure TypeScript intent matcher — ~200 lines, zero dependencies, zero download, sub-50 ms response, works offline, works on every device.

Is it "real AI"? No — and that's the point. It doesn't pretend to. It's a well-engineered information retrieval system.

For a portfolio: Interviewers consistently rate "built a system" higher than "wrapped an API". This feature demonstrates algorithmic thinking — normalization, scoring, priority, tie-breaks — not prompt engineering.

11 Part 2 · Architecture

1. User types a question in any language
2. Client calls askAssistant(query) Server Action
3. detectIntent(query) normalizes + scores against 10 intents
4. Priority tie-break if two intents score equal
5. Winning intent's response pulled from current locale
6. Response returned in < 50 ms, no external API

Three files, three responsibilities

FileResponsibility
knowledge-base.tsPure data — 10 intents, each with keyword lists in all 7 languages
matcher.tsPure algorithm — normalize, score, dedupe, priority tie-break
actions/assistant.tsOrchestration — call matcher, fetch translation, return reply

Why this separation matters: The matcher is testable in isolation (npx tsx -e "..." — one command), and the knowledge base can grow to 30+ intents without touching any other file.

12 Part 2 · Knowledge Base

Ten intents × 7 languages = ~70 keyword lists, but only ~120 total keywords because many are shared across Romance and Germanic languages.

export const INTENT_KEYWORDS: Record<IntentKey, string[]> = {
  cancel: [
    "cancel", "cancellation", "modify", "change my", "reschedule",
    "الغاء", "الغيت", "الغي", "تعديل", "اغير", "ااجل",
    "annuler", "annulation", "modifier", "changer",
    "stornieren", "stornierung", "andern", "verschieben",
    "cancelar", "cancelacion", "cambiar", "modificar",
    "annullare", "annullamento", "cambiare", "modificare",
    "取消", "改期", "修改",
  ],
  // ... 9 more intents
};

Two design decisions:

  • Keywords are pre-normalized in the source. No accents, no diacritics, no Arabic tashkeel. The matcher normalizes user input the same way, so both sides compare on equal footing. This makes the file more readable and stable.
  • Keywords list every plural form explicitly. Romance languages have inflected plurals (vegetariano / vegetariani), and the matcher uses word boundaries for Latin scripts — so vegetarian won't match vegetarianos. Listing plurals is simpler and more predictable than adding a stemmer.

13 Part 2 · Intent Matcher

A pure function with no side effects. Give it a query string, get back an intent or null.

export function detectIntent(rawQuery: string): IntentKey | null {
  const query = normalize(rawQuery);
  if (!query) return null;

  let bestIntent: IntentKey | null = null;
  let bestScore = 0;

  for (const [intentKey, keywords] of Object.entries(INTENT_KEYWORDS)) {
    const intent = intentKey as IntentKey;
    let score = 0;
    const seen = new Set<string>();

    for (const keyword of keywords) {
      const kw = normalize(keyword);
      if (!kw || seen.has(kw)) continue;
      seen.add(kw);

      const isLatin = /^[a-z0-9 ]+$/.test(kw);
      const matched = isLatin
        ? new RegExp(`\\b${escapeRegex(kw)}\\b`).test(query)
        : query.includes(kw);

      if (matched) score += kw.length >= 4 ? 2 : 1;
    }

    // ... priority tie-break (next section)
  }

  return bestScore >= MIN_SCORE ? bestIntent : null;
}

The normalize() function

function normalize(text: string): string {
  return text
    .toLowerCase()
    .normalize("NFD")
    .replace(/[\u0300-\u036f]/g, "")        // Latin diacritics: é → e
    .replace(/[\u064B-\u065F\u0670]/g, "")  // Arabic tashkeel
    .replace(/[إأآ]/g, "ا")                  // Arabic alef variants
    .replace(/ى/g, "ي")                      // Arabic alef maqsura
    .replace(/ة/g, "ه")                      // Arabic ta marbuta
    .replace(/\s+/g, " ")
    .trim();
}

Why this is critical: A user typing réservation (French with accent) and a user typing reservation (no accent) should both match the same keyword list. Similarly, Arabic users typing مواعيد vs مَوَاعِيد (with tashkeel) should both match.

Scoring rules

CaseScoreRationale
Keyword length ≥ 4+2Longer keywords are more specific
Keyword length < 4+1Short keywords like "map" could match unrelated words
Latin keywordsword-boundary matchreserve won't match preserved
Arabic / CJK keywordssubstring matchNo clear word boundaries in these scripts

14 Part 2 · Priority Tie-Break

The subtle bug Query: "cancel my reservation". This matches both intents:
  • cancel — via keyword "cancel" (score 2)
  • reservation — via keyword "reservation" (score 2)

Tie. Which one wins?

The wrong approach: rely on the order of keys in knowledge-base.ts. This is fragile — reordering the file would silently break behavior.

The right approach: an explicit PRIORITY array — priority as a policy decision, not an implementation detail.

// Lower index = higher priority on tie
const PRIORITY: IntentKey[] = [
  "cancel",       // specific action on a booking
  "allergies",    // safety concern
  "halal",        // dietary requirement
  "vegetarian",   // dietary preference
  "events",       // specific occasion
  "parking",      // specific facility
  "location",     // info request
  "hours",        // info request
  "reservation",  // general topic
  "menu",         // most general
];

const PRIORITY_INDEX = new Map<IntentKey, number>(
  PRIORITY.map((k, i) => [k, i])
);

Tie-break logic

const isBetter =
  score > bestScore ||
  (score === bestScore && score > 0 && candidatePriority < currentPriority);

if (isBetter) {
  bestScore = score;
  bestIntent = intent;
}

Three cases:

  1. Higher score → always wins (score > bestScore)
  2. Tie, higher priority → wins (score === bestScore && candidatePriority < currentPriority)
  3. Tie, lower priority → keeps the existing winner

Why "cancel beats reservation"

Cancelling is a specific action on a general concept. Every "cancel" query is also about a reservation, but not every "reservation" query is about cancelling. When a user types cancel my reservation, they're overwhelmingly asking about cancellation — the intent with the word reservation is just context.

The general principle When two intents tie, the more specific one wins. This is a well-known heuristic in information retrieval — used in search engines, recommendation systems, and email spam filters. Being explicit about the priority order documents the policy in code.

15 Part 2 · The Duplicate Keyword Bug

Discovered by adding debug logging 
{ intent: 'cancel', score: 2, bestScore: 0, bestIntent: null }
{ intent: 'reservation', score: 4, bestScore: 2, bestIntent: 'cancel' }
                                              ↑↑↑ should be 2
Reservation scored 4 instead of 2 — so the priority tie-break never even ran.

Root cause: The keyword "reservation" appears twice in the array — once under the English comment, once under the French comment. Both got counted, doubling the score.

reservation: [
  "reserve", "reservation", "book", "booking", "table for",  // English
  ...
  "reserver", "reservation", "reserv",                       // French
                ↑↑↑ duplicate
],

The fix: dedupe at the matcher level

let score = 0;
const seen = new Set<string>();

for (const keyword of keywords) {
  const kw = normalize(keyword);
  if (!kw || seen.has(kw)) continue;   // ← dedupe here
  seen.add(kw);
  // ...
}

Why this fix, and not the "obvious" one: We could have removed the duplicate from the knowledge base. But that only fixes today's bug. Tomorrow, adding a new language that shares a word with English (e.g., adding Portuguese, where "menu" is also "menu") would reintroduce it. Deduping in the matcher is idempotent, defensive, and forward-proof.

After the fix 
cancel my reservation       → cancel    ✅
je veux annuler ma réservation → cancel   ✅
book a table                → reservation ✅

16 Part 2 · Server Action

"use server";

import { getTranslations } from "next-intl/server";
import { detectIntent } from "@/lib/assistant/matcher";
import type { IntentKey } from "@/lib/assistant/knowledge-base";

export type AssistantReply = {
  intent: IntentKey | null;
  text: string;
};

export async function askAssistant(query: string): Promise<AssistantReply> {
  if (!query || typeof query !== "string" || query.trim().length < 2) {
    const t = await getTranslations("Assistant");
    return { intent: null, text: t("fallback") };
  }

  const t = await getTranslations("Assistant");
  const intent = detectIntent(query);

  if (!intent) {
    return { intent: null, text: t("fallback") };
  }

  const textMap: Record<IntentKey, string> = {
    hours: t("intents.hours"),
    location: t("intents.location"),
    parking: t("intents.parking"),
    reservation: t("intents.reservation"),
    cancel: t("intents.cancel"),
    menu: t("intents.menu"),
    allergies: t("intents.allergies"),
    vegetarian: t("intents.vegetarian"),
    halal: t("intents.halal"),
    events: t("intents.events"),
  };

  return { intent, text: textMap[intent] };
}

Why an explicit map instead of a template literal: next-intl v4 has strict typing for t(). A dynamic key like t(\`intents.${intent}\`) may or may not satisfy the compiler depending on the project config. The explicit map is type-safe, self-documenting, and turns the intent list into a compile-time checklist — if you add an 11th intent, TypeScript errors until you add its entry.

20 The Errors Journey

Five real bugs surfaced during Phase 13 — each one taught a specific lesson.

🎯 Error 1 — Cannot find module './it.json'

GET /it 500 · MODULE_NOT_FOUND
Fix: Clear .next cache and restart. Webpack caches the module context for dynamic imports; adding a new locale file doesn't invalidate it.

🎯 Error 2 — IntentKey not exported from matcher

Module '"./matcher"' declares 'IntentKey' locally, but it is not exported.
Fix: Import IntentKey from its source (knowledge-base.ts) where it's defined, not from the file that consumes it. Type definitions belong where they're created.

🎯 Error 3 — French cancel lost to French reservation

"je veux annuler ma réservation" → returned reservation reply
Fix: Priority tie-break — explicit array, not object-key order. Cancel beats reservation on tie.

🎯 Error 4 — Spanish plural not matched

"¿hay mesas vegetarianas?" → returned fallback
Fix: Added explicit plural forms to the vegetarian keyword list. Word boundaries don't stem — plural "vegetarianas" must be listed separately.

🎯 Error 5 — Duplicate keyword inflates score by 2×

Debug log: reservation scored 4 (should be 2) because "reservation" appears in both English and French blocks
Fix: Dedupe keyword strings inside the matcher loop with a Set<string>. Defensive — prevents future languages from re-triggering the bug.
