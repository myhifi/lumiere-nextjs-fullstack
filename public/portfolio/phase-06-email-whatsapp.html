Phase 06 · Email + WhatsApp

Email Notifications & WhatsApp Integration

Deliver transactional emails to guests after every successful reservation and provide a one-tap WhatsApp channel for inquiries — all without requiring any paid service or credit card. Uses the Strategy Pattern for swappable providers and fail-safe delivery so email failures never break a reservation.

1 Overview

Goal: Send Arabic confirmation emails to guests when a reservation is created — and keep a fast, one-tap WhatsApp channel always available — without breaking the bank or violating the strict no-card policy.

Deliverables

6 Email Types — types.ts

export type EmailProviderName = "console" | "resend";

export type ReservationEmailData = {
  to: string;
  guestName: string;
  reservationId: string;
  tableNumber: number;
  reservationDate: Date;
  guestsCount: number;
};

export type SendEmailResult = {
  success: boolean;
  messageId?: string;
  error?: string;
};
  • EmailProviderName — union type narrows EMAIL_PROVIDER to exactly two valid values. Typos become compile errors.
  • ReservationEmailData — the canonical input shape for every email template. New templates (cancel, reminder) reuse this shape or extend it.
  • SendEmailResult — uniform return contract. All providers must return this shape. Callers don't branch per provider.
  • messageId? optional — console returns a fake ID; resend returns a real one.
  • error? optional — populated only on failure.

Why these three types live in one file: They form the interface of the email subsystem. Any provider or template imports from here. One file to review for API shape changes.

export function ReservationConfirmation({
  guestName, reservationId, tableNumber,
  reservationDate, guestsCount,

  const shortId = reservationId.slice(0, 8).toUpperCase();

  return (
    <Html dir="rtl" lang="ar">

      <Preview>{`تم استلام حجزك في Lumière — طاولة رقم ${tableNumber}`}</Preview>

}
  • Omit<ReservationEmailData, "to"> — the template doesn't need the recipient address; excluding it prevents accidental misuse.

10 Why Inline Styles — The Email Client Constraint

The core problem: Email clients are stuck in 2005.

FeatureWeb BrowserGmailOutlook
<link rel="stylesheet">✅❌ Stripped❌ Stripped
<style> block✅⚠️ Partial❌ Mostly stripped
External CSS variables✅❌❌
inline style=""✅✅✅

The only universally supported approach: inline style attributes on every element.

React Email solves this elegantly:

  • You write styles as JavaScript objects.
  • render() from @react-email/components converts them to inline style="" attributes during HTML generation.
  • Component tree stays readable; output is 2005-compatible.

import type { ReservationEmailData, SendEmailResult } from "../types";

export async function sendViaConsole(
  data: ReservationEmailData,
  html: string
): Promise<SendEmailResult> {
  const line = "═".repeat(60);

  console.log("\n" + line);
  console.log("📧 [DEV] إيميل جاهز للإرسال (لم يُرسل فعلياً)");
  console.log(line);
  console.log(`   إلى:      ${data.to}`);
  console.log(`   الموضوع:  تأكيد حجزك في Lumière — طاولة رقم ${data.tableNumber}`);
  console.log(`   المعرّف:  ${data.reservationId}`);
  console.log(line);
  console.log("📄 محتوى HTML (مقتطف):");
  console.log(html.slice(0, 400) + "...");
  console.log(line);
  console.log("💡 للتبديل إلى Resend: أضف EMAIL_PROVIDER=resend في .env\n");

  return { success: true, messageId: `console-${Date.now()}` };
}
  • async even though there's no await — because the caller awaits it. Making it sync would force a different calling convention per provider. Uniform interface wins.
  • html.slice(0, 400) — truncates the HTML preview. Full HTML is thousands of characters; dumping it would drown the terminal.
  • messageId: \`console-${Date.now()}\` — mimics a real provider's response. Callers depending on a messageId keep working.

12 send.ts Facade — Provider Selection

import { render } from "@react-email/components";
import { ReservationConfirmation } from "./templates/ReservationConfirmation";
import { sendViaConsole } from "./providers/console";
import type {
  EmailProviderName, ReservationEmailData, SendEmailResult,
} from "./types";

function getProvider(): EmailProviderName {
  const provider = process.env.EMAIL_PROVIDER as EmailProviderName | undefined;
  return provider ?? "console";
}

export async function sendReservationConfirmation(
  data: ReservationEmailData
): Promise<SendEmailResult> {
  try {
    const html = await render(
      ReservationConfirmation({
        guestName: data.guestName,
        reservationId: data.reservationId,
        tableNumber: data.tableNumber,
        reservationDate: data.reservationDate,
        guestsCount: data.guestsCount,
      })
    );

    const provider = getProvider();

    switch (provider) {
      case "console":
        return await sendViaConsole(data, html);

      case "resend":
        console.warn("[email] Resend provider not implemented yet, falling back to console");
        return await sendViaConsole(data, html);

      default:
        return { success: false, error: `مزوّد إيميل غير معروف: ${provider}` };
    }
  } catch (error) {
    console.error("[sendReservationConfirmation] error:", error);
    return { success: false, error: "فشل تجهيز الإيميل" };
  }
}
  • render() — React Email's core function. Converts a React element tree into an HTML string. Runs on the server; zero client bytes.
  • process.env.EMAIL_PROVIDER as EmailProviderName | undefined — process.env values are always string | undefined. The cast narrows the type; runtime validation happens in the switch default case.
  • provider ?? "console" — safe default if .env is missing the key.
  • default: case — defensive. If .env contains a typo (EMAIL_PROVIDER=consle), the return shape is still SendEmailResult with a clear error.

13 .env Configuration

# ─── Email Provider ───
# console = print to terminal (development)
# resend  = real delivery (requires API key)
EMAIL_PROVIDER=console

HOW: send.ts reads process.env.EMAIL_PROVIDER at call time.

WHY runtime read: Unlike some config that is read once at boot, this read happens per email. In development, you can flip the provider by editing .env and — thanks to Next.js hot-reloading the environment — the next submission uses the new provider without restarting the server.

17 Fail-Safe Design — Nested try/catch

The two-layer protection:

OUTER try / catch
Wraps ALL database operations
If it catches: reservation failed → return { success: false }
INNER try / catch
Wraps ONLY the email send
If it catches: reservation SUCCEEDED, log the error silently, do NOT return success: false
Return: { success: true } — reservation is safe
Failure scenarioCorrect outcome
Database write failssuccess: false — user must retry
Email provider fails, DB succeededsuccess: true — reservation is safe

Why the customer must not see the email failure:

  • The reservation exists in the database.
  • The admin can manually resend the email.
  • Showing an error to the user creates confusion ("Is my table booked?").
Anti-pattern avoided 
// ❌ Bad pattern
const reservation = await prisma.reservation.create(...);
await sendReservationConfirmation(...);   // If this throws → outer catch → success: false
return { success: true };
Without the inner try/catch, an email failure would bubble up to the outer handler and incorrectly report the reservation as failed.

19 Contact Constants — lib/constants/contact.ts

export const CONTACT = {
  // WhatsApp number in international format, no "+", no spaces
  // Example: 201001234567 (Egypt)
  whatsappNumber: "201001234567",

  whatsappDefaultMessage:
    "مرحباً Lumière! أرغب في الاستفسار عن حجز طاولة.",

  email: "hello@lumiere.example",
  phone: "+20 100 123 4567",
  address: "القاهرة، مصر",
} as const;

export function getWhatsAppLink(message?: string): string {
  const text = encodeURIComponent(message ?? CONTACT.whatsappDefaultMessage);
  return `https://wa.me/${CONTACT.whatsappNumber}?text=${text}`;
}
  • as const — freezes the object literal. CONTACT.whatsappNumber is typed as the literal "201001234567", not string. Catches typos.
  • whatsappNumber — the wa.me format requires no +, no spaces, no dashes. Just digits with country code.
  • getWhatsAppLink() — accepts an optional custom message. When called with no argument, uses the default.
  • encodeURIComponent — Arabic text and spaces must be URL-encoded. مرحباً becomes %D9%85%D8%B1%D8%AD%D8%A8%D8%A7%D9%8B. Without this, WhatsApp would receive garbled text.

21 WhatsApp Button Deep-Dive

target="_blank" and rel="noopener noreferrer"

  • target="_blank" — opens WhatsApp Web in a new tab, preserving the restaurant site in the original tab.
  • rel="noopener" — prevents the new tab from accessing window.opener (a class of phishing / tab-nabbing attacks).
  • rel="noreferrer" — hides the referrer URL from WhatsApp. Privacy best practice.
  • Both attributes are mandatory when using target="_blank".

fixed bottom-6 left-6 z-50

  • fixed — position relative to viewport, unaffected by scrolling.
  • bottom-6 left-6 — 24px from bottom-left corner.
  • Why left, not right: In RTL layouts, the "natural" empty corner shifts. WhatsApp buttons in Arabic UIs conventionally sit bottom-left.
  • z-50 — highest Tailwind z-index tier. Stays above modals, navbars, and images.

bg-[#25D366] and hover:bg-[#1ebe5a]

  • [#25D366] — arbitrary-value syntax. Bypasses the theme palette for this one case.
  • Why not add to @theme: This color is WhatsApp's brand identity, not Lumière's. Adding it to the theme would be semantically wrong.

hidden md:inline

  • The text label "تواصل معنا" appears only on screens ≥ 768px.
  • Why: On mobile, the round icon alone is clear; extra text wastes screen space.

aria-label and aria-hidden

  • aria-label on the anchor — screen readers announce "تواصل معنا عبر واتساب" even when the text is hidden.
  • aria-hidden on the <svg> — prevents the SVG from being read twice.

23 Request Data Flow — Full Trace

1. User on /reserve fills form → clicks "تأكيد الحجز"
2. Client Component calls createReservation(formData)
─── SERVER BOUNDARY ───
3. Server Action executes:
a. Zod validates input
b. Prisma queries tables within ±3h window
c. findBestTable() returns optimal table
4. Prisma INSERTs reservation row
5. Inner try/catch: sendReservationConfirmation()
i. render() converts React template → HTML string
ii. getProvider() reads EMAIL_PROVIDER=console
iii. sendViaConsole() prints to terminal
6. Return { success: true, reservationId, tableNumber }
─── CLIENT BOUNDARY ───
7. Success screen replaces form

Boundary rationale:

  • Server Action input/output serialization is handled by Next.js transparently.
  • The email dispatch happens after the database write — the reservation is durable before any network call.
  • The inner try/catch isolates the network operation from the transactional operation.
