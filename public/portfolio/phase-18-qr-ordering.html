Phase 18 · QR Table Ordering

The Physical-Digital Bridge

Allow customers to scan a QR code at their table, browse the menu, and order instantly. Implement Dine-In workflows with optional contact details and a seamless Cash/Card payment toggle.

Zustand PersistenceQR Code Generation URL StateDynamic Zod Validation Cash Payment Flow

1 Overview

Goal: Enable physical table ordering via QR codes and handle Dine-In specific requirements (like skipping delivery addresses and allowing cash payments).

Key Deliverables

  • QR Code Generator: Admin UI to generate and print high-resolution QR codes for each table.
  • Table Detection: A Zustand-backed URL parser that detects ?table=5 and locks the cart to Dine-In mode.
  • Dine-In Checkout: Hides the delivery address and phone number fields, replacing them with a "Pay by Card / Pay by Cash" toggle.
  • Cash Payment Bypass: Cash orders bypass Stripe entirely, immediately setting the order status to PAID and triggering the Kitchen Display and Email receipt.

2 QR Code Generation

We used the qrcode package to generate Base64 Data URLs on the server. This avoids needing to store physical image files.

// src/actions/qrcode.ts
const targetUrl = `${baseUrl}/${locale}/menu?table=${tableNumber}`;

const dataUrl = await QRCode.toDataURL(targetUrl, {
  width: 600,
  margin: 2,
  color: { dark: "#1a1a1a", light: "#ffffff" },
});
return { success: true, dataUrl, targetUrl };

The Admin UI uses a custom modal that displays the QR code and includes a "Print" button which opens a clean, branded print window.

3 Customer Flow & Table Detection

When the customer scans the QR, they land on /menu?table=5. A Client Component reads the URL and saves it to the Zustand store.

// src/components/menu/TableDetector.tsx
useEffect(() => {
  if (tableParam && tableParam !== tableNumber) {
    setTableNumber(tableParam);
  }
}, [tableParam, tableNumber, setTableNumber]);
Persistence is Key The tableNumber is saved in localStorage via Zustand's persist middleware. This ensures that if the user refreshes the page or navigates to the cart, the table number is not lost.

4 Cash & Dine-In Checkout

In a real restaurant, asking for a delivery address at the table is poor UX. We made the Zod schema dynamic.

// src/lib/validations/order.ts
guestPhone: z.string().trim().optional().refine((val) => {
  if (!val) return true; // Valid for Dine-In
  return /^[+\d\s\-()]+$/.test(val) && val.length >= 8;
}, t("guestPhoneInvalidChars")),

deliveryAddress: z.string().trim().min(5).max(200).optional(),
paymentMethod: z.enum(["CARD", "CASH"]).default("CARD"),

For Cash orders, the Server Action skips Stripe, marks the order as PAID, deducts stock, and dispatches the Resend confirmation email immediately.

// src/actions/checkout.ts
if (data.paymentMethod === "CASH") {
  await sendOrderConfirmation({ ... }); // Instant receipt
}
return { success: true, orderId: order.id };
The Resend 403 Error During testing, Cash orders triggered a 403 error from Resend. This was because the Resend Free Tier strictly limits sending to the account's registered email address. In production with a verified domain, this works flawlessly.

5 Engineering Lessons

  • Base64 vs File Storage: Generating QR codes as Base64 strings eliminates the need for S3/Cloudinary buckets and avoids broken image links.
  • Zustand Persistence: Always explicitly include critical context variables (like tableNumber) inside the partialize block of your Zustand store, or they will be lost on page refresh.
  • Optional Zod Fields: When making a field optional in Zod, always ensure you send undefined rather than an empty string "", otherwise .min(5) validation will fail silently.
  • Business Logic > Tech: Allowing Cash payments requires bypassing the Stripe Webhook entirely and triggering the post-payment side effects (email, KDS) directly inside the Server Action.
