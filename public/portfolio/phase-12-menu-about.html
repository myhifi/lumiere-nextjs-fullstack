1 Overview

Goal: Close three user-experience gaps that surfaced after Phase 11 shipped: menu items still showing Arabic on English pages, form errors hidden below the fold, and a missing About page. Each is a distinct problem requiring a distinct fix — all delivered in one cohesive phase.

Deliverables

  1. Bilingual menu items — add nameEn + descriptionEn columns to MenuItem, populate 12 dishes, and localize rendering via getLocalizedName().
  2. Admin form upgrade — two new optional English fields per dish, with a clear explanation of the edge case when the admin interface is in English.
  3. Category dropdown localization — admin category selects show English names on non-Arabic locales.
  4. Auto-scroll to first error — reusable hook applied to all 6 forms, using smooth scroll + delayed focus.
  5. About page — 5-section story page with hero, story, chef bio, values, and CTA, fully translated in 5 locales.
  6. Navbar 5th link — About between Menu and Reserve, with per-locale labels.
  7. Scroll-to-top button — fade-in after 400px, positioned bottom-right (opposite WhatsApp).
  8. Bilingual 404 handling — two layers: Next.js root fallback + Vercel static page for missing files.

2 Three Features, One Phase

Three seemingly separate requests converged into one cohesive phase, because they share infrastructure and design patterns.

🍽️ Bilingual Menu

Extends the getLocalizedName() pattern already proven with Category.nameEn. Same migration strategy, same helper, same admin UX.

Built once as a hook. Applied to 6 forms. Solves a real-world problem: silent errors that hide below the fold after submit.

📖 About Page

Why bundle them? Each feature is small enough to fit in one session, and all three share the same release commit — keeping the git history clean and the Vercel deploy atomic.

5 Part 1 · Schema — Add Two Nullable Columns

The pattern: Extend the existing Category.nameEn approach to the MenuItem model. Two new String? fields — optional, never blocking, backward compatible.

model MenuItem {
  id             String   @id @default(cuid())
  name           String
  nameEn         String?           // ← NEW
  slug           String   @unique
  description    String?
  descriptionEn  String?           // ← NEW
  price          Float
  imageUrl       String?
  isAvailable    Boolean  @default(true)
  isFeatured     Boolean  @default(false)
  ...
}

Why these are nullable

ScenarioResult
Existing dish has no English translationDB stores null
Admin skips the English fieldDB stores null
Non-Arabic user views the dishFalls back to Arabic via ?? in the helper
Zero-downtime migration Because the columns are nullable, the migration is non-breaking. Production data continues to work; only new writes populate the English fields.

7 Part 1 · Idempotent Backfill Script

The problem: Vercel production has live data. Running npm run db:seed would wipe reservations and demo history.

The solution: A dedicated script that updates in place — one row at a time, matched by slug.

// scripts/update-menu-items-en.ts
const UPDATES = [
  { slug: "lentil-soup", nameEn: "Lentil Soup",
    descriptionEn: "Traditional lentil soup with cumin and lemon" },
  // ... 11 more entries
];

for (const update of UPDATES) {
  await prisma.menuItem.update({
    where: { slug: update.slug },
    data: {
      nameEn: update.nameEn,
      descriptionEn: update.descriptionEn,
    },
  });
}
PropertyValue
Destructive?❌ No — only touches 2 columns
Idempotent?✅ Yes — running twice is safe
Prod-safe?✅ Yes — no DELETE, no TRUNCATE
Fails loudly?✅ process.exit(1) on any error

8 Part 1 · getLocalizedName() Extension

The core insight: A single helper function decides which value to render, based on the current locale.

export function getLocalizedName(
  name: string,
  nameEn: string | null | undefined,
  locale: string
): string {
  if (locale === "ar") return name;
  return nameEn ?? name;
}

Behavior table

LocalenameEn present?Renders
ar—Arabic name (always)
en/fr/de/es✅ YesEnglish nameEn
en/fr/de/es❌ NoFalls back to Arabic name
One helper, all content types The same function handles Category.name, MenuItem.name, and MenuItem.description — the shape of the arguments is identical: (arValue, enValue, locale).

11 Part 1 · Category Dropdown Fix

Bug caught during manual testing The menu item form's category dropdown showed Arabic names (مقبلات, أطباق رئيسية) even on English admin pages.

Root cause: The admin pages fetched categories with select: { id, name, slug } — no nameEn — so the data was Arabic by default.

Fix: Add nameEn to the select, then map through getLocalizedName() before passing to MenuItemForm.

const categoriesRaw = await prisma.category.findMany({
  orderBy: { displayOrder: "asc" },
  select: { id: true, name: true, nameEn: true, slug: true },
});

const categories = categoriesRaw.map((cat) => ({
  id: cat.id,
  name: getLocalizedName(cat.name, cat.nameEn, locale),
  slug: cat.slug,
}));

Where the fix was applied

File
src/app/[locale]/admin/menu/new/page.tsx
src/app/[locale]/admin/menu/[id]/edit/page.tsx
Lesson Whenever admin pages surface DB content as labels for other admins, they must run through getLocalizedName() just like public pages. The rule isn't "public pages localize" — it's "any content the user sees localizes."

12 Part 1 · The "English Admin" Trade-off

The situation: An English admin logs into /en/admin/menu/[id]/edit. The form shows both a main "Dish Name" field (containing the Arabic name) and an "English Name" field (containing the English name).

Option A — Hide the EN fields

On /en/admin/*, hide the EN fields entirely. Mirror the main fields into the EN columns on submit.

Problem: If the admin edits a bilingual dish, the Arabic name overwrites the English one when they save. Silent data loss.

Option B — Keep them visible ✅

Always show both fields. Accept the "duplicate-looking" UI on English admin. Document the trade-off.

Chosen because: Zero silent data loss. Theoretical edge case documented for a future Phase 13 refinement.

Why this is the right call for now: The real admin is Arabic-speaking. The "English admin" is a portfolio-demo scenario. Hiding fields to solve a cosmetic "duplication" issue silently corrupts bilingual data — the wrong trade-off.

Future refinement (Phase 13 candidate) On /en/admin/*, rename the main field label from "Dish Name" to "Arabic Dish Name" and the EN field to "English Dish Name". This makes the purpose explicit without hiding data.

13 Part 2 · The Real Problem

Observed in manual testing Admin fills a form. Clicks "Add Dish". Nothing visible happens — the error message is 700px above, off-screen. Admin assumes the internet broke, or the app is stuck, or the button didn't register.

Root cause: When validation fails, errors appear inline next to their fields. If the field is scrolled out of view, the user has no signal about what happened.

14 Part 2 · Why "Error Near Button" is Wrong

The instinctive fix — a badge near the submit button saying "3 errors" — is a common anti-pattern. It was proposed but rejected. Here's why.

ApproachUser steps neededVerdict
Badge near button1. Notice badge · 2. Scroll up · 3. Find field · 4. Read error · 5. Fix❌ 5 steps
Auto-scroll to error1. See scroll · 2. Read error · 3. Fix✅ 3 steps
Toast notification1. Read toast · 2. Scroll up · 3. Find field · 4. Fix❌ Toast disappears before scroll

What real products do

  • Stripe Checkout — scrolls to first error field
  • GitHub settings — scrolls + focuses the first invalid input
  • Shopify admin — scrolls + focuses
  • Google Forms — scrolls + red highlight
  • Vercel deployments — same pattern
The industry standard Auto-scroll is universal. Users' eyes follow the scroll motion; they land on the error naturally. No second action required.

15 Part 2 · The useScrollToFirstError Hook

A single hook, applied to all 6 forms. Built once, used everywhere — modular design.

export function useScrollToFirstError(
  fieldErrors: Record<string, string[]> | undefined
) {
  useEffect(() => {
    if (!fieldErrors) return;
    const firstKey = Object.keys(fieldErrors)[0];
    if (!firstKey) return;

    const timer = setTimeout(() => {
      const input = document.querySelector(`[name="${firstKey}"]`);
      if (!(input instanceof HTMLElement)) return;

      input.scrollIntoView({ behavior: "smooth", block: "center" });

      setTimeout(() => {
        if (input instanceof HTMLInputElement ||
            input instanceof HTMLTextAreaElement ||
            input instanceof HTMLSelectElement) {
          input.focus({ preventScroll: true });
        }
      }, 400);
    }, 50);

    return () => clearTimeout(timer);
  }, [fieldErrors]);
}

The three clever details

DetailWhy
setTimeout(…, 50)Lets React paint the error message first — otherwise layout height shifts mid-scroll and the target moves
setTimeout(…, 400) before focusLets the smooth-scroll animation finish before focus moves — otherwise focus triggers a second native scroll that fights the smooth one
focus({ preventScroll: true })Focus the input without letting the browser scroll again. The user just watched the scroll — they don't need a second one

Why document.querySelector instead of refs

  • Simpler — no ref threading through every form
  • Scoped to [name="..."] — collision risk is negligible since forms render one at a time
  • Server Actions return fieldErrors keyed by input name — perfect match

16 Part 2 · Applied to 6 Forms

Two lines per form. Same pattern across all of them.

The pattern (4 forms with local state)

const [fieldErrors, setFieldErrors] = useState({});

useScrollToFirstError(
  Object.keys(fieldErrors).length > 0 ? fieldErrors : undefined
);

The pattern (2 forms with result state)

Reservation and Review use a discriminated union result — the errors live under result.fieldErrors:

const [result, setResult] = useState<Result>({ kind: "idle" });

useScrollToFirstError(
  result.kind === "error" ? result.fieldErrors : undefined
);

Forms updated

The ReviewForm exception

Review's "Please select a star rating" error lives at the bottom of the form, right above the submit button. Since users are already at the bottom when they click submit, the error is already visible. No scroll needed.

Why the hook silently does nothing here The star rating error is a cross-field result.message, not a result.fieldErrors[fieldName]. The hook looks for fieldErrors — finds none — returns early. Perfect.

20 Bonus · Scroll-to-Top Button

A small circular button that appears after 400px of scroll, positioned bottom-right (opposite the WhatsApp button on the bottom-left).

Design decisions

DecisionRationale
SHOW_AFTER_PX = 400Industry standard (Stripe, Tailwind docs use 300-500px)
Fade + slide-inOpacity + 12px translate — subtle motion, not jarring
Physical right-6 (not logical end-6)WhatsApp is also physically at left-6. Keeping both physical preserves ergonomics across RTL/LTR
48×48px circularBig enough to tap on mobile, small enough not to compete with content
Icon only (SVG chevron)No text label — aria-label handles accessibility
pointer-events-none when hiddenInvisible button doesn't intercept clicks
 
useEffect(() => {
  function handleScroll() {
    setVisible(window.scrollY > SHOW_AFTER_PX);
  }
  handleScroll();
  window.addEventListener("scroll", handleScroll, { passive: true });
  return () => window.removeEventListener("scroll", handleScroll);
}, []);
Passive scroll listener { passive: true } tells the browser the handler won't preventDefault() — enables the browser's hardware-accelerated scroll optimizations.

21 Bonus · Root 404 Pages

Two independent 404 layers — one for Next.js routes, one for Vercel's CDN.

Layer 1 — Next.js route 404

src/app/not-found.tsx catches any unmatched route not inside a valid [locale] prefix.

Requirement discovered the hard way Root-level not-found.tsx must include its own <html> and <body> tags — because the root layout is a passthrough (returns children), not a full document. Without these tags, Next.js throws "Missing <html> and <body> tags in the root layout."

The Client Component conversion

Two ESLint/TypeScript errors surfaced:

ErrorCauseFix
react/no-unescaped-entitiesRaw apostrophes in "you're" / "Don't"Use &apos;
Type 'string' is not assignable to 'MouseEventHandler'onClick="history.back()" — string form works in HTML, not JSXConvert to "use client" + arrow function

Layer 2 — Vercel static 404

public/404.html is served by Vercel's CDN before Next.js runs, for missing static files. It has no access to NEXT_LOCALE or URL context — so it's bilingual English + Arabic with inline CSS.

Two layers, two purposes
  • Next.js layer — for missing app routes (/en/wrong-page)
  • Vercel layer — for missing static files (/old-image.png, /legacy.html)

22 The Errors Journey

Nine distinct issues surfaced during Phase 12 — each one teaches a specific lesson.

🎯 Error 1 — Prisma Studio shows English names in DB

Migration + seed work, but Prisma Studio shows nameEn filled — expected this time ✅
Lesson: When a migration adds nullable columns, db:seed populates them; update-menu-items-en.ts fills existing prod rows. Two paths for two environments.

🎯 Error 2 — VS Code stale TS after migration

Property 'nameEn' does not exist on type 'MenuItem'
Fix: Ctrl + Shift + P → TypeScript: Restart TS Server. Terminal tsc --noEmit was silent — the IDE was holding a stale Prisma Client in memory.

🎯 Error 3 — alt attribute still Arabic in English pages

Right-click image on /en/menu/hummus → alt="حمص بالطحينة"
Fix: The <Image alt={item.name}> on the item detail page was the "hidden 4th" localization spot. Changed to alt={localizedName}.

🎯 Error 4 — "Try again" button didn't recover

Clicking Try Again re-renders the same error — user must refresh browser
Fix: router.refresh() before reset(). The RSC payload was cached with the error state; refreshing busts the cache, then reset clears the boundary.

🎯 Error 5 — Root 404 missing document tags

Missing <html> and <body> tags in the root layout.
Fix: Root not-found.tsx must provide its own <html> + <body>, because the root layout is a passthrough, not a full document.

🎯 Error 6 — ESLint no-unescaped-entities

`'` can be escaped with `&apos;`, `&lsquo;`, `&#39;`, `&rsquo;`
Fix: Replace you're → you&apos;re, Don't → Don&apos;t. ESLint's React rules require escaped entities for cleanliness.

🎯 Error 7 — onClick string in Server Component

Type 'string' is not assignable to type 'MouseEventHandler<HTMLButtonElement>'
Fix: onClick="history.back()" works in plain HTML but not JSX. Convert file to "use client" + onClick={() => window.history.back()}. Also replaces the metadata export with explicit <meta> tags.

🎯 Error 8 — AboutPageProps removed but still used

Cannot find name 'AboutPageProps'
Fix: Restore the type declaration. Only the page body should drop params; generateMetadata still needs the type to extract locale.

🎯 Error 9 — Tailwind canonical class hint

The class `aspect-16/9` can be written as `aspect-video`
Fix: Rename to aspect-video. Warning only, but matches Tailwind's canonical vocabulary.
