Phase 14 · Stripe Checkout & Ordering

Food Delivery & Event-Driven Payments

Transform Lumière from a reservation-only platform into a fully functional delivery service. Implement a client-side shopping cart using Zustand, integrate Stripe Checkout Sessions, and process payments securely via Event-Driven Webhooks to update inventory and order statuses.

1 Overview

Goal: Add a shopping cart and a secure, production-ready checkout pipeline that handles dynamic line items, calculates totals, and reacts to successful payments.

Deliverables

  1. Database: Add Order and OrderItem models to track purchases and snapshot prices.
  2. Cart State: Persistent client-side cart using Zustand + localStorage.
  3. Checkout UI: A seamless drawer, delivery details form, and quantity selectors.
  4. Stripe Session: Server Action to map DB items to Stripe line_items and redirect to payment.
  5. Webhook Handler: Route Handler that verifies Stripe signatures, updates orders to PAID, and decrements stock atomically.
  6. Admin Dashboard: A new page to view delivery orders and update their fulfillment status.

2 Database Updates

We added an Order and OrderItem model. The most critical architectural decision here is snapshotting the price (priceAtOrder). If the restaurant changes the price of a dish tomorrow, yesterday's orders must retain the original price they paid.

model Order {
  id                    String      @id @default(cuid())
  guestName             String
  guestEmail            String
  guestPhone            String
  deliveryAddress       String
  status                String      @default("PENDING")
  totalAmount           Float
  stripeSessionId       String?     @unique
  stripePaymentIntentId String?     @unique
  items                 OrderItem[]
  // ...
}

model OrderItem {
  id           String   @id @default(cuid())
  orderId      String
  order        Order    @relation(fields: [orderId], references: [id], onDelete: Cascade)
  menuItemId   String
  menuItem     MenuItem @relation(fields: [menuItemId], references: [id], onDelete: Restrict)
  quantity     Int
  priceAtOrder Float    // CRITICAL: Snapshot the price
}
Stock Management We added a stock Int @default(100) column to MenuItem. This allows the webhook to decrement available inventory the moment payment succeeds.

3 Zustand Shopping Cart

For the cart, we avoided using the database for every quantity change (which would cause massive DB load). We used Zustand with the persist middleware to store the cart in localStorage.

export const useCartStore = create<CartState>()(
  persist(
    (set, get) => ({
      items: [],
      addItem: (item) => set((state) => { /* ... logic */ }),
      getTotal: () => get().items.reduce((total, item) => total + item.price * item.quantity, 0),
    }),
    { name: "lumiere-cart-storage" }
  )
);

Why this is production-ready: It allows guests to fill their cart without needing an account, survives page refreshes, and uses zero database connections until they click "Checkout".

4 Stripe Checkout Session

When the user submits the checkout form, a Server Action fetches the real prices from the database (never trusting the client) and creates a Stripe Session.

const lineItems = order.items.map((item) => ({
  price_data: {
    currency: "AED",
    product_data: { name: item.menuItem.name },
    unit_amount: Math.round(item.priceAtOrder * 100), // AED uses 2 decimals
  },
  quantity: item.quantity,
}));

const session = await stripe.checkout.sessions.create({
  mode: "payment",
  line_items: lineItems,
  client_reference_id: order.id,
  success_url: `${siteUrl}/${locale}/checkout/success?session_id={CHECKOUT_SESSION_ID}`,
  cancel_url: `${siteUrl}/${locale}/cart`,
});

5 Secure Event-Driven Webhooks

The biggest flaw in the legacy MERN app was relying on the browser to confirm payment. We built a Route Handler at /api/webhooks/stripe to handle this securely.

Idempotency & Atomic Updates

Stripe can send the same webhook multiple times. To prevent double-stock deduction, we check the order status first. Then, we use a Prisma Transaction to update the order and deduct inventory simultaneously.

if (existingOrder.status === "PAID") {
  return NextResponse.json({ received: true }); // Idempotency check
}

await prisma.$transaction(async (tx) => {
  await tx.order.update({
    where: { id: orderId },
    data: { status: "PAID", stripePaymentIntentId: session.payment_intent },
  });

  for (const item of existingOrder.items) {
    await tx.menuItem.update({
      where: { id: item.menuItemId },
      data: { stock: { decrement: item.quantity } },
    });
  }
});
Testing with Stripe CLI We used stripe listen --forward-to localhost:3000/api/webhooks/stripe --events checkout.session.completed to test the payment flow locally without exposing the dev server to the internet.

6 Admin Orders Dashboard

To manage the incoming food orders, we built an admin dashboard that respects the existing RBAC (Role-Based Access Control).

  • Server Component: Fetches all orders joined with their items.
  • Client Component (OrderRow): Displays customer details, delivery address, and totals.
  • Status Updates: A dropdown allows Staff to transition the order from PAID → PREPARING → DELIVERED.
  • Audit Log: Every status change is logged with the user's name and the before/after state.

7 The Errors Journey

1. Prisma P2024: Connection Pool Timeout

Cause: Neon Serverless DB going to sleep + 9 parallel queries on the Admin Dashboard.

Fix: Appended &pgbouncer=true&connection_limit=5 to the DATABASE_URL.

2. React Hydration Mismatch on Cart Badge

Cause: Zustand instantly read localStorage on the client, but the server rendered 0 items.

Fix: Wrapped the badge in an isMounted check (using useEffect with an ESLint disable comment).

3. Recharts Reversed Text (`150 - 101`)

Cause: The SVG tooltip inherited RTL text-direction from the document (or parsed the hyphen as a minus sign).

Fix: Forced direction: "ltr" in the Recharts contentStyle and used En-dashes (–) for the label ranges.

8 Engineering Lessons

  • Never trust the client. When creating Stripe sessions, always fetch the item prices from the database to prevent users from manipulating the price in the DOM.
  • Snapshots are mandatory. priceAtOrder ensures that historical financial records are never affected by future menu price updates.
  • Idempotency is critical. Webhooks can retry. Always check if a record has already been updated before executing a transaction.
  • Zustand + persist is the sweet spot for e-commerce carts, avoiding unnecessary DB load while surviving page refreshes.
