Phase 03 · API Layer

Route Handlers, Prisma Singleton & Dynamic Routes

Build the HTTP API layer that exposes the database to any external consumer — mobile app, Postman, third-party integration — using Next.js Route Handlers with a consistent JSON envelope and discipline around HTTP status codes.

Route HandlersPrisma Singleton Dynamic RoutesREST APIHTTP Status Codes

1 Overview

Goal: Expose the seeded database through HTTP endpoints that any external consumer can use — without coupling them to the frontend.

Deliverables

  1. src/lib/prisma.ts — Prisma Client singleton (hot-reload safe, absolute SQLite path).
  2. GET /api/menu/categories — returns all categories with item counts.
  3. GET /api/menu/items — returns all items with ?category=, ?featured=, ?limit= filters.
  4. GET /api/menu/items/[slug] — returns a single item by slug, or 404.
  5. Consistent JSON envelope: { success, data } or { success, error }.

2 Route Handler vs Server Action vs Server Component

Server Actions ("use server")Internal form submissions from React componentsPhase 5 (reservations)
Server ComponentsDirect DB access from page componentsPhase 4 (menu UI)
Legacy API Routes (pages/api/)Next.js < 13 pattern❌ Deprecated
Engineering rationale Route Handlers are the only API style producing a stable public URL. Server Actions are opaque RPC endpoints — not shareable, not testable via Postman, not consumable by a mobile app. The menu must be consumable by external systems, so Route Handlers win.

6 Why a Prisma Singleton?

The hot-reload problem

  1. Developer saves a file.
  2. Next.js dev server reloads the module graph (HMR).
  3. Every reload executes new PrismaClient() again.
  4. Each client opens a new database connection pool.
  5. After ~20 saves, the pool exceeds SQLite/Postgres limits.
  6. Errors: Too many clients, SQLITE_BUSY, or silent hangs.

The Singleton fix: Store one PrismaClient instance on globalThis. On reload, reuse it.

src/lib/prisma.ts — Full File

import path from 'node:path'
import { PrismaClient } from '../generated/prisma/client'

const globalForPrisma = globalThis as unknown as {
  prisma: PrismaClient | undefined
}

const sqlitePath = path
  .join(process.cwd(), 'prisma', 'dev.db')
  .replace(/\\/g, '/')

export const prisma =
  globalForPrisma.prisma ??
  new PrismaClient({
    datasourceUrl: `file:${sqlitePath}`,
    log: ['error', 'warn'],
  })

if (process.env.NODE_ENV !== 'production') {
  globalForPrisma.prisma = prisma
}

Line-by-line rationale

  • import path from 'node:path' — Node's path utility; the node: prefix is ESM best practice.
  • globalThis as unknown as {...} — TypeScript cast so globalThis.prisma is type-safe.
  • path.join(process.cwd(), 'prisma', 'dev.db') — builds an absolute path from the project root.
  • .replace(/\\/g, '/') — normalizes Windows backslashes to forward slashes for URI format.
  • ?? (nullish coalescing) — reuse existing instance if present, else create new.
  • datasourceUrl — overrides the .env value at runtime (fixes the path resolution bug — see next section).
  • NODE_ENV !== 'production' — only cache globally in dev (production has no HMR).

7 The SQLite Path Resolution Bug & Fix

Symptom encountered Error querying the database: Error code 14: Unable to open the database file GET /api/menu/categories 500 in 10.2s

Root cause: DATABASE_URL="file:./dev.db" in .env is relative. Its meaning depends on who reads it:

ConsumerWorking DirectoryResolves ToWorks?
prisma migrateprisma/prisma/dev.db✅
prisma studioprisma/prisma/dev.db✅
prisma db seedprisma/prisma/dev.db✅
next dev runtimeproject root./dev.db (wrong!)❌

The fix: In src/lib/prisma.ts, compute an absolute path at runtime:

const sqlitePath = path.join(process.cwd(), 'prisma', 'dev.db')

WHY this is portable:

  • process.cwd() always returns the project root when Next.js runs.
  • No hardcoded D:\... paths — works on any machine.
  • CLI tools keep using .env (relative) — no change needed there.

Production note: When migrating to PostgreSQL (Phase 9), datasourceUrl will be removed and .env will hold the hosted URL directly (no relative path issue exists for network URLs).

8 GET /api/menu/categories

import { NextResponse } from 'next/server'
import { prisma } from '@/lib/prisma'

export async function GET() {
  try {
    const categories = await prisma.category.findMany({
      orderBy: { displayOrder: 'asc' },
      select: {
        id: true,
        name: true,
        slug: true,
        description: true,
        _count: {
          select: { items: true },
        },
      },
    })

    return NextResponse.json({
      success: true,
      data: categories,
    })
  } catch (error) {
    console.error('[GET /api/menu/categories]', error)
    return NextResponse.json(
      { success: false, error: 'فشل تحميل التصنيفات' },
      { status: 500 }
    )
  }
}

HOW: Named export GET matches the HTTP method. Next.js invokes it for GET /api/menu/categories.

WHY this shape: Consistent { success, data } envelope lets clients branch on success without parsing HTTP status text.

9 Query Deep-Dive — select, _count, orderBy

orderBy: { displayOrder: 'asc' }

Sorts categories by the numeric displayOrder column. WHY: Admin controls menu order without editing code.

select: { id, name, slug, description }

Returns only the listed fields. WHY: Reduces payload size; prevents leaking future sensitive fields (e.g., internalNotes).

_count: { select: { items: true } }

Prisma's relation-count aggregation. Generates SELECT COUNT(*) FROM menu_items WHERE categoryId = ... per row. WHY: The UI shows "3 items" per category without a second query. One request, zero N+1.

Example response

  "success": true,

      "id": "cmu...",
      "name": "مقبلات",
      "slug": "appetizers",
      "description": "أطباق خفيفة...",
      "_count": { "items": 3 }

}

10 GET /api/menu/items with Filters

import { NextRequest, NextResponse } from 'next/server'
import { prisma } from '@/lib/prisma'

export async function GET(request: NextRequest) {
  try {
    const { searchParams } = new URL(request.url)
    const categorySlug = searchParams.get('category')
    const featured = searchParams.get('featured')
    const limit = searchParams.get('limit')

    const items = await prisma.menuItem.findMany({
      where: {
        isAvailable: true,
        ...(categorySlug && { category: { slug: categorySlug } }),
        ...(featured === 'true' && { isFeatured: true }),
      },
      orderBy: [{ isFeatured: 'desc' }, { name: 'asc' }],
      take: limit ? parseInt(limit, 10) : undefined,
      include: {
        category: {
          select: { id: true, name: true, slug: true },
        },
      },
    })

    return NextResponse.json({ success: true, data: items })
  } catch (error) {
    console.error('[GET /api/menu/items]', error)
    return NextResponse.json(
      { success: false, error: 'فشل تحميل الأطباق' },
      { status: 500 }
    )
  }
}

11 Query Deep-Dive — Spread Conditions & include

The spread-condition pattern

...(categorySlug && { category: { slug: categorySlug } })

How it works:

  • If categorySlug is truthy → spreads { category: { slug: '...' } } into where.
  • If categorySlug is null → spreads false (Prisma ignores non-objects).

WHY instead of if/else: Keeps the query as a single expression. Composable: add more filters without nested branches.

include vs select

KeywordBehaviorUse When
selectReturns only the listed fieldsYou know exactly what you need
includeReturns all scalar fields + relationsYou want everything plus relation data

Here: include returns all item fields + a trimmed category object.

13 GET /api/menu/items/[slug] (Dynamic Route)

import { NextRequest, NextResponse } from 'next/server'
import { prisma } from '@/lib/prisma'

type RouteParams = {
  params: Promise<{ slug: string }>
}

export async function GET(request: NextRequest, { params }: RouteParams) {
  try {
    const { slug } = await params

    const item = await prisma.menuItem.findUnique({
      where: { slug },
      include: {
        category: {
          select: { id: true, name: true, slug: true },
        },
      },
    })

    if (!item) {
      return NextResponse.json(
        { success: false, error: 'الطبق غير موجود' },
        { status: 404 }
      )
    }

    return NextResponse.json({ success: true, data: item })
  } catch (error) {
    console.error('[GET /api/menu/items/[slug]]', error)
    return NextResponse.json(
      { success: false, error: 'فشل تحميل الطبق' },
      { status: 500 }
    )
  }
}

HOW: Folder [slug] captures any URL segment as a string.

WHY params: Promise<...>: Next.js 15+ made route params async to support streaming metadata. await params is mandatory.

14 Query Deep-Dive — findUnique and 404 Handling

findUnique({ where: { slug } })

  • Compiles to SELECT * FROM menu_items WHERE slug = ? LIMIT 1.
  • Requires slug to have a @unique constraint (it does — Phase 2).
  • WHY findUnique not findFirst: findUnique uses the DB index directly; findFirst scans. Faster + guarantees zero ambiguity.

404 handling

if (!item) {
  return NextResponse.json(
    { success: false, error: 'الطبق غير موجود' },
    { status: 404 }
  )
}

WHY explicit 404 instead of throwing:

  • Throwing produces a generic 500.
  • Clients must distinguish "resource missing" (404, do not retry) from "server broken" (500, retry).
  • Browser DevTools confirms via Failed to load resource: 404.

15 HTTP Status Code Discipline

StatusMeaningUsed In
200SuccessAll GET routes on success
400Bad Request — malformed inputPhase 5: Zod failures
404Not Found — resource missing/items/[slug] no match
500Server Error — unexpectedAny caught exception

WHY explicit codes matter:

  • CDNs, load balancers, and monitoring tools route on status.
  • 404 responses are not cached the same way 200 responses are.
  • Mobile apps can apply retry logic only for 5xx.
Anti-pattern avoided Returning 200 for "not found" with { success: false } — breaks HTTP semantics and confuses clients.

16 Response Envelope Design

Success

{ "success": true, "data": <payload> }

Failure

{ "success": false, "error": "رسالة عربية واضحة" }

WHY this contract:

  • Single branching point: if (response.success) { ... } else { show(response.error) }.
  • Arabic error messages are ready to display directly.
  • Future extensibility: add meta: { pagination } alongside data without breaking clients.

17 Request Data Flow — Trace a Single Call

Flow for GET /api/menu/items?category=desserts:

1. Browser → GET /api/menu/items?category=desserts
2. Next.js router matches → app/api/menu/items/route.ts → GET()
3a. new URL(request.url) → extracts searchParams
3b. searchParams.get('category') → "desserts"
3c. Spreads { category: { slug: 'desserts' } } into where
4. Prisma → SQL:
SELECT ... FROM menu_items
WHERE isAvailable = 1 AND categoryId IN (...)
ORDER BY isFeatured DESC, name ASC
5. SQLite engine executes → returns rows
6. Prisma deserializes → TypeScript objects
7. NextResponse.json → serializes to JSON string
8. Response: 200, Content-Type: application/json

Boundary rationale: Each transition (URL → object → SQL → JSON) validates shape. Any mismatch fails loudly and early.

18 Why Not fetch() Between Server Components and API?

Question: Now that we have /api/menu/items, should the menu page fetch it?

Answer: No — the menu page queries prisma directly.

ApproachNetwork hopsSerializationLatency
Page → fetch('/api/menu/items') → Server → DB2 (loopback + DB)JSON twiceHigh
Page → prisma.menuItem.findMany() → DB1 (DB only)NoneMinimal

WHY keep both:

  • Route Handlers exist for external consumers: mobile apps, partners, webhooks, Postman.
  • Server Components consume the database directly: internal, zero network, zero JSON.
This is the core value of Next.js Full-Stack The internal API layer is optional, not mandatory.

19 Request Lifecycle — Server vs Client Boundaries

CLIENT (Browser)
• HTML, CSS, minimal JS
• No Prisma, no DATABASE_URL, no secrets
HTTP (JSON over TLS in production)
SERVER (Node.js on Vercel / localhost)
• Route Handler executes here
• Prisma Client instantiated here
• dev.db / Postgres accessed here

Boundary rationale: The client never touches the database. Every byte of data crossing the boundary is explicitly shaped by NextResponse.json(). Secrets never leak.
